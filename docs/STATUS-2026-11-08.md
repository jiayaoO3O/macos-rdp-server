### 1.1 分辨率/黑边方案（2026-11-08 最终版）

- 客户端**连接时**请求的桌面框 = 会话分辨率（例如 2560x1440）。服务端在会话开始时创建
  **同尺寸的 16:9 虚拟显示器**（1x，pixels == points），把物理显示器镜像到它，由
  ScreenCaptureKit 直接按桌面框采集 → Worker 1:1 输出（`event=peer_frame_layout ...
  offset=0,0 scaled=0`），**无黑边、无拉伸、无裁切**。
- 断开/崩溃时自动解除镜像并恢复原显示模式（虚拟显示器随子进程退出被 WindowServer 移除）。
- 客户端重连到不同分辨率时，按新桌面框创建新的虚拟显示器（已实测 2560→1080→2560）。
- 设计/实测细节：[DESIGN-2026-11-08-virtual-display.md](DESIGN-2026-11-08-virtual-display.md)。

## 2. 明确不在当前范围 / 已知限制

1. **DISP 会话中窗口缩放实时改分辨率：不可用（客户端限制）**。真实 mstsc 不发
   MS-RDPEDISP monitor layout；服务端 DISP 通道已实现并有诊断日志，但窗口拖动不会触发
   会话分辨率变化。分辨率在**连接时**生效；需要新分辨率时重连即可（会按新尺寸创建虚拟显示器）。
   证据与客户端分析见 [DIAGNOSIS-2026-11-08-disp-window-resize.md](DIAGNOSIS-2026-11-08-disp-window-resize.md)
   （该文档的"黑边"部分已由虚拟显示器方案取代，DISP 部分仍有效）。
2. **无物理显示器时不创建虚拟显示器**：笔记本合盖（clamshell）或没有外接显示器时，
   服务端检测不到可镜像的物理屏，会记录 `event=virtual_display_skipped
   reason=no_physical_display` 并回退 fit-with-bars（可能带黑边），不会留下幽灵显示器。
   生产目标是**无头 Mac mini 4 + 外接 4K 16:9 显示器**（物理屏存在，方案适用；该硬件
   路径尚未真机验证，4K 16:9 面板本身预期天然无黑边）。
3. **多显示器排列**：v1 只支持单物理显示器（保存/恢复该屏模式）；多显示器快照/恢复未实现。
4. **远程登录/解锁、锁屏采集、多用户并发、音频重定向、文件系统重定向**：不在范围（P0 边界）。
5. **H.264/AVC420（GFX）**：实验性，`avc420` build tag + 手工 `.deps/install-h264`，未部署；
   默认 Worker 不含该依赖。
6. **TCC 身份**：`bin/RDPAgent.app` 为 ad-hoc 签名；**重新打包后 cdhash 变化可能再次弹权限框**。
   文件剪贴板读取受保护目录（桌面/文稿/下载/容器）时，Worker 直接读原路径；若被 TCC 拒绝
   （`clipboard_file_rejected reason=unreadable name=... errno=1`），需给 `RDPAgent.app`
   **完全磁盘访问**并启用 Agent 暂存（`RDP_AGENT_CLIPBOARD_STAGING=1`，默认关闭）。
7. **Windows App（macOS 客户端）**：DISP 行为分析基于旧版 Windows App；当前验收客户端是
   Windows 11 `mstsc.exe`。Windows App 的 DISP 是否可用未再验证。
8. 开发原型：无 Developer ID 稳定签名/公证、无安装器/自动更新、无系统 LaunchDaemon、无限流/失败锁定/审计。
9. **菜单栏 App/DMG 的限制**：adhoc 签名（重打包 cdhash 变化 → 其他机器可能需重授权/重走
   Gatekeeper 右键打开）；未公证；仅 arm64；内置自绘 AppIcon（`scripts/generate-app-icon.py` 生成）；LAN 证书 SAN 只在启动时按当前
   私有 IPv4 生成（地址变化后 Worker 跟随但证书不热更新，重启 App 即重新生成）；Worker 每帧
   一行日志（~60/s），App 只在启动时轮转日志（>32 MiB → `.1`）。
10. **键盘输入**：根因已定案并修复（nil-source CGEvent 继承陈旧 Fn 位；见 §1 表格与
    [DIAGNOSIS-2026-11-08-keyboard-swallowed-input.md](DIAGNOSIS-2026-11-08-keyboard-swallowed-input.md) §9），
    真机验收通过。原手动「释放卡住按键」按钮（SIGUSR1）已于 2026-11-09 移除（根因修复后不再需要；
    自动释放路径保留：peer release-all / socket close / receiver error / 所有退出路径）；
    `RDP_AGENT_EVENT_TAP=1`（事件 flags 探针）与 `RDP_AGENT_INPUT_TRACE=1` 保留为 opt-in 诊断开关
    （默认关闭；采样后删除含按键码的 trace 日志）。

- **运行态（generation/PID/监听地址/进程）每次不同，必须用命令现查**：`pgrep -fl 'RDPServer|rdp-worker'`、`RDPServer --status`、`launchctl print gui/$(id -u)/com.rdp-server.agent`、`lsof -nP -iTCP:3389 -sTCP:LISTEN`。文档不写死快照。
  诊断用 `RDP_AGENT_INPUT_TRACE=1`/`RDP_AGENT_EVENT_TAP=1` 默认关闭。
- **2026-11-09 鼠标修复落地**：macOS 26.x 工作机（Apple Silicon）安装带修复的候选构建后已真机确认鼠标对齐；
  `main` 已合入源码修复 `e13c9d3` 并与 pipe2 构建修复合并；`dist/` 已重建为组合包（未真机复测）。
  若尚未重启 App，运行中的仍是旧二进制；下次重启 App 才用新包，ad-hoc 签名变化可能需要重新授权屏幕录制/辅助功能。
- **已解决（macOS 26.5.1）**：同一旧包只在 macOS 26 崩溃、macOS 27 不崩。9 份 `.ips` 将故障定位到 WinPR `CreateEventA → winpr_event_init` 中通过 weak-import 调用 `_pipe2`；macOS 26.5.1 的 `libSystem` 没有此导出。修复为 pipe()+fcntl，并关闭 `WINPR_HAVE_PIPE2`；已确认 11:03 修复包在 Mac 上启动成功。见 §1.2。
- **制品校验**：发布前对 DMG、`Contents/Helpers/{rdp-worker,rdpctl}` 与嵌套 agent 记录校验和；具体值以当次构建为准，不在文档中固定。
- **旧 `.runtime/` 部署**（`bin/rdp-worker` + LaunchAgent `com.rdp-server.agent`）是**另一套状态**，
  与 App 数据目录互不读写；旧 LaunchAgent 若仍安装会指向旧 `agent-compat.sock` 反复重试。
  **如需卸载旧 LaunchAgent，可执行 `python3 scripts/agent-launchd.py uninstall`**，并确认 plist、launchd 服务与残留 socket 一并清理。
  **不要两套同时占用 3389。**

### 3.2 部署/回滚（详见 [AGENTS.md](../AGENTS.md) §6）

```sh
# 构建（会覆盖 bin/，即当前部署产物）
make build && make agent-build && make agent-app
shasum -a 256 bin/rdp-worker bin/RDPAgent.app/Contents/MacOS/rdp-agent

# Worker 重启（会断开活动会话；需维护者确认）
kill -TERM <worker-supervisor-pid>; # 等 child 退出
rm -f .runtime/agent-compat.sock   # 必须！否则 C 侧静默放弃 Agent 监听（reason=no_frame）
nohup ./bin/rdp-worker -config .runtime/config.json -agent-socket .runtime/agent-compat.sock >> .runtime/worker-live.log 2>&1 &

# Agent 重启（不断会话）
launchctl kickstart -k gui/$(id -u)/com.rdp-server.agent
bin/RDPAgent.app/Contents/MacOS/rdp-agent status
```

- **Worker + Agent 是硬匹配对**（尤其文件剪贴板 IPC 13–16）：同窗口成对部署/回滚。
- 回滚快照：私有目录下按功能与日期保存的旧 worker/agent 二进制（如 `.runtime/rollback-pre-<feature>-<date>/`）。
- 虚拟显示器功能回滚：把 wrapper 中 `RDP_AGENT_VIRTUAL_DISPLAY=1` 去掉/改 0 后 kickstart
  Agent（代码默认关闭；回退后回到 fit-with-bars）。

### 3.3 环境前提

- **笔记本开发机需保持盖子打开**（或外接显示器）：合盖时没有物理显示器，虚拟显示器功能
  自动跳过（回退 fit）。合盖还会让 WindowServer 移除内建屏，导致 Agent 缓存显示失效——
  重启 Agent 可恢复；不要在有活动会话时合盖。
- 文件剪贴板：worker 直接读原路径；受保护目录需给 `RDPAgent.app` 完全磁盘访问。
- 不要在对外服务的 3389 长时间开 `WLOG_LEVEL=DEBUG` / `RDP_TRANSPORT_DUMP`（体积巨大且含会话流量）。

## 5. 架构与关键契约（速查）

- 拓扑：Windows 客户端 → FreeRDP Worker（Go + cgo C）↔ 私有 Unix socket（RDPA v1）↔
  Swift Agent（ScreenCaptureKit / CGEvent / NSPasteboard）。
- IPC：12B 头 `RDPA` + v1 + type(u16 BE) + len(u32 BE)；类型 2/7/10/11/12 帧、3 输入、
  8 文本剪贴板、9 桌面尺寸、13–16 文件剪贴板、17 恢复显示模式；未知类型忽略并限频日志。
- 分辨率：客户端桌面框 = 协商尺寸；虚拟显示器让 capture == desktop（1:1）；鼠标坐标
  Worker 原样转发（仅 clamp），Agent 负责 desktop→capture→points 映射（1:1 时恒等）。
  **输入 display target（2026-11-09 契约）**：虚拟显示器 active 且其 bounds 尺寸==capture 时，注入必须用虚拟屏
  （mirror master / capture framebuffer）的 displayID 与 `CGDisplayBounds`；否则回退启动物理屏 bounds（fit-with-bars 路径）。
  诊断日志 `event=input_target source=virtual|physical`、`event=input_target_fallback reason=bounds_mismatch|display_unavailable`。
- 剪贴板文件：≤100 文件、单文件 <2GiB、总 ≤4GiB、文件名安全单路径组件、符号链接/非普通文件拒绝；
  Agent 落地目录 `NSTemporaryDirectory()/rdp-clipboard*/`（0700/0600、O_EXCL|O_NOFOLLOW）。
- 详细契约：[DESIGN-2026-11-07-resolution-adaptation.md](DESIGN-2026-11-07-resolution-adaptation.md)、
  [DESIGN-2026-11-08-clipboard-files.md](DESIGN-2026-11-08-clipboard-files.md)、
  [DESIGN-2026-11-08-virtual-display.md](DESIGN-2026-11-08-virtual-display.md)。
